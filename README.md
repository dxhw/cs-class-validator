# CSCI 1710: Final Project

## What did we do?

In this project, we sought to create models of the most common Brown University Computer Science undergraduate concentration requirements, focusing primarily on exploring the differences in the "pure" CS concentrations introduced in 2024 for both the ScB and the AB. Students, especially those in the 2026 and 2027 class years, are faced with a great number of similar and overlapping sets of requirements if they're interested in a computing-focused degree, each of which are structured differently and place different constraints on what students may take. Based on experience and peer testimony, navigating these constraints and requirements can be difficult for students to manage and fully appreciate. However, each concentration is, in essence, a required set of course codes with certain logical conditions, presenting a strong opportunity for modelling and solving. 

We aimed to create a model that could both validate existing course plans against different concentration requirements and also highlight the gaps in these course plans if they do not fulfill the requirements. Additionally, we wanted to expand the scope of our midterm project to include the CS AB, the new CS concentration requirements, and the most common joint concentrations. Both of these goals expand heavily on the work done in our midterm project, which only explored the structure of the old CS ScB without validation or further course guidance. We believe we have successfully achieved both of these goals in our project, as our model can determine if a course plan satisfies the concentration requirements or has needed additional courses under current requirements for MATH-CS, APMA-CS, CS-ECON, Computational Biology, and the pure CS AB and ScB under both the pre and post-2024 requirements.

## What is our model?

In developing our model, we focused on building out the groups of courses that might exist in each concentration, which different course codes might fulfill. These groups constitute the core of our model, which produce a set of constraints that the SMT solver may reason against. This allows our model to approach each degree from a "concentration-first" standpoint, where we attempt to consider how the described natural-language constraints might limit which courses might slot into a particular requirement. This is in contrast to our midterm, which took a "courses-first" approach, where every possible course has particular attributes that may interact with each other to build a degree under some global constraints. From our perspective, the concentration-first stance is the essence of our model and allows for greater extensibility and flexibility in reasoning about the concentrations at Brown. This also allows our model to at least partially cope with new courses, changes to certain degree requirements, and to use course codes that students already use. 

Many CS-related concentrations also have several footnotes that try to limit or expand course options under some specific conditions. Non-exhaustively, these include multiple courses only counting for 1 credit, specific courses only counting within requirements in conjunction with other courses, and course equivalencies. We have attempted to model many of these special cases to the best of our ability, but these are less rigorously verified and validated given the small number of students these cases impact overall. For offering potential courses that may complete an incomplete degree, the model will use courses that could reasonably exist given the degree requirements, but there is no explicit attempt to determine if these courses actually exist as options available to students. The model does not include any notion of prerequisites or relationships between courses, since we intend the models to be used as validators, not necessarily as degree planning tools. Relatedly, the model does not attempt to account for half-credit or double-credit courses, courses that are taken together, or any notion of whether a course plan would complete global degree requirements at Brown. We also make no attempt at modelling courses that might be manually approved by a concentration advisor and, for capstone courses, whether a student has actually utilized that course as a capstone. The model also intentionally assumes that all courses have been taken at Brown, which excludes transfer, AP, and IB credits. Concentrations, ultimately, are socially negotiated and validated by concentration advisors, the relevant departments, and Brown itself, which are difficult to model in a deterministic way! Given this, the model accounts for most Brown CS students in most cases, but there are many edge and corner cases that we intentionally leave out for this project. 

## How does this work?

The model operates by building a large matrix of boolean variables, structured as `use_{course}_for_{category}`, that indicate whether a course is used for a certain category within the degree. Throughout the code, these variable often wrapped inside `If(var, 1, 0)` expressions, which provide 1 if a course is used in the category and 0 if not. We can sum these if statements across all of the course variables to produce constraints about a requirement category, such as having 3 course that are in a group of electives. For courses that don't fit a category, we simply add `Not(var)` to our model to prevent it from being used. This allows the solver to only "switch on" the courses that are valid for each category, using the implied constraints that fall out of the categories together to produce a valid concentration. To be clear, most requirement categories--each with their own function--produce a single constraint over all of valid courses for a category, resulting in a large but limited number of constraints for the solver to reason about. While likely not the most efficient method, course plans often end up being small enough (<40 courses) with relatively few requirement categories in the concentration (<10 categories) that determining if a degree plan satisfies the requirements is basically instantaneous. 

## How does this run?

All of our code for this project is in the `z3-model` folder. We use the cs1710 environment with Python 3.10 to run our code. Any earlier python version will fail to run.

Our code runs in `validator.py`. We have a CLI for running our code with arguments. These are:
 - `-h, --help`:              help message and exit
 - `--year YEAR`:             your graduation year
 - `--degree_type {SCB,AB}`:  your degree type (AB/SCB), default is SCB
 - `--degree {CS,CompBio,CS+ECON,MATH+CS,APMA+CS}`: the degree you're getting
 - `--requirement_version {Old,New,Either}`: The version of requirements that you are using (Old/New), default is New
 - `--courses COURSE_JSON_FILE`: the JSON file with the courses you'd like to evaluate

We recommend adding a test schedule JSON to the `test_schedules` folder to test out a degree plan for yourself!

Our test file runs using pytest. Executing `pytest testing.py` in the `z3-model` folder will run our tests.

## What did we learn?

We found that the CS-related degrees at Brown are, broadly, highly complex and frequently non-descriptive as to what, exactly, counts for each degree. This is also worsened by the joint degrees, which each have a significant number of special cases that must be accounted for and, frequently, more limited options overall. While many requirements are written so that they might be more flexible for students, this flexibility often ends up being conditional in a way that can be confusing and suggest potential double-counting or course overlaps where there are none. This is worse for students wishing to take advantage of the Open Curriculum and broaden their horizons beyond their concentration, as these students will have a more limited set of course slots for their degree and will need to plan much more to ensure they can graduate. Even merely being able to check what courses might fit into different degrees or slots automatically is incredibly useful for verifying that someone is on the right track to graduate. Despite the numerous limitations of the model listed above, we find this to be an extremely useful tool for Brown CS students.
